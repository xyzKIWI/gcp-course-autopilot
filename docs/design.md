# 設計：時間窗內的多步驟表單工作流程

以內建模擬平台為例。平台的形狀是許多伺服器渲染的線上課程系統都有的樣子：一張「學員卡」列出各步驟的狀態；報名、簽到、簽退、問卷、選擇題測驗各自是一張表單；每一步都有開放時間窗；前一步沒完成，後一步不能做；有些動作（例如測驗）只記最後一次結果。

這類流程的難處不在「怎麼按按鈕」，而在：**錯過時間窗就作廢、重複送出可能有副作用、頁面隨時可能改版、而你無法在旁邊盯著。**

## 分工

| 程式 | 何時跑 | 做什麼 | 用不用 AI |
|---|---|---|---|
| `register.py` | 報名窗開啟時（例如每天早上） | 報名符合條件的課程 | 不用 |
| `runner.py` | 每 60 秒 | 預檢、簽到、簽退、問卷、測驗、驗收、通知 | 只有測驗作答、以及頁面改版時的備援 |

原則：**能用確定性程式做的，就不用 AI。**

## 1. 報名（參考實作）

1. 讀取課程列表，依政策篩選：免費、線上、報名窗內，並通過你自己的 `schedule_ok()`（例如接行事曆，避開已有行程）；
2. **每次執行最多送出一門**，不論結果；
3. **送出前把意圖寫進磁碟**；
4. 回到平台的報名列表，**看到這門課與報名序號才算成功**；
5. 意圖存在但查不到報名 → 不重送，通知人。

輸出的 `registrations.json` 就是 `runner.py` 讀的課程清單（`runner.py` 只讀不寫）。

## 2. 上課日

`runner.py` 被排程每 60 秒叫醒一次；**沒有當天（或近 3 天未結案）的已報名課程、也沒有待送通知時，就立刻結束、不連網**。

| 時間 | 動作 | 驗收 |
|---|---|---|
| 設定的預檢時間後第一次執行 | 登入、學員卡上恰有一張此課程的卡、序號相符 | 通知「預檢通過／異常」 |
| 簽到窗開後 1 分鐘 | 取得簽到表單（逐欄核對）→ 送出 | 卡片「簽到」欄變成合法時間戳 |
| 簽退窗開後 1 分鐘 | 簽退 → 問卷 → 測驗，依序進行 | 各欄依序出現時間戳；測驗出現 0–100 分數 |

**前一步沒完成，下一步不做。** 前一步的時間窗已過而未完成，只會觸發通知，後面的步驟不會執行。

## 3. 選擇題測驗

1. 程式抓題目與選項；
2. 若卡片上有附件連結，且主機在允許清單內（平台本身＋設定的 `material_hosts`），下載 PDF（大小、頁數、時間都有上限、轉址只跟隨到允許的主機）並抽取文字——這段文字會送給作答供應商；
3. 題目＋文字交給第一個設定的作答供應商，要求回傳 `{"answers": {...}, "uncertain": [...]}`，JSON schema 以題號與選項字母鎖死；
4. 程式驗證：每題都有、答案是合法選項、`uncertain` 只含題號；不合格就換下一個供應商；
5. **送出前再看一次時鐘**，把「待確認」（送出前的卡片值）寫進磁碟；
6. 送出後檢查平台回應是否含成功訊息（收據），再回讀卡片；
7. **只有出現分數才結案**：達及格分數 → 完成；未達 → 把上次分數與答案告訴模型重答一次；兩次都未達 → 通知人；
8. 已達及格分數就**絕不重答**（只記最後一次的平台可能因此蓋掉好成績）；卡片上既有的、或人工更新的分數都會被偵測並計入次數。

## 4. 失敗時

| 狀況 | 行為 |
|---|---|
| 第一次失敗 | 立刻通知，窗內持續重試 |
| 網路錯誤（送出前） | 下一分鐘重試（每步最多 3 次） |
| 送出後結果不明 | 不重送；卡片沒變就停手通知 |
| 表單或卡片結構改變 | 交給備援代理人**一次**（先把「已啟動」寫進磁碟，程式當掉重開也不會再叫一次） |
| 備援失敗或剩餘時間不足 | 依實際情況通知（不會把沒啟動的代理人寫成「作答後 60 分」） |
| 時間窗結束仍未完成 | 最後讀一次卡片：完成就記完成，未完成就通知 |
| 課程結束後卡片被平台移除 | 通知「無法確認」，並列出程式紀錄中未完成的步驟 |
| 本機狀態檔損毀 | 另存壞檔、重新開始，當天測驗改為人工（避免失去「待確認」證據後重送） |

## 5. 演練

- `--dry-run`：登入並讀取狀態、印出「會做什麼」；不寫任何本機檔案、不送任何會改變狀態的表單、不呼叫 AI、不通知。可搭配 `--now <ISO 時間>` 模擬時間點。
- `--status`：印出狀態檔。
- 接到任何真實系統之前，先在模擬平台跑 `demo.py` 與全部測試。
